# 学习资源生成内容质量优化方案 v4

## 1. 目标与结论

本方案针对当前五类学习资源：

- `concept_map`
- `code_snippet`
- `interactive_exercise`
- `video_summary`
- `diagnostic_quiz`

优化重心不是单纯增加篇幅，而是提高以下六项质量：

1. **事实准确**：关键教学声明能够回溯到知识库证据。
2. **教学有效**：资源围绕明确、可检验的学习目标组织。
3. **个性化真实有效**：根据掌握度、近期错误和学习阶段改变教学策略，而不只是把用户字段塞进 prompt。
4. **资源间一致且互补**：五张卡共享同一教学蓝图，不互相矛盾，也不重复改写同一段定义。
5. **练习可验证**：代码、练习、诊断题均有可执行或可判定的正确性依据。
6. **质量可衡量**：建立离线评测、线上学习效果指标和版本化发布闭环。

建议将当前 `resource-v3` 演进为 `resource-v4`，保留现有异步作业、缓存、SSE 和概念图优先展示架构，重点重构“上下文准备 -> 教学蓝图 -> 分卡生成 -> 质量校验 -> 定向修复 -> 效果反馈”这一内容链路。

## 2. 当前代码的主要质量问题

### P0-1：资源落库没有真正启用事实一致性校验

涉及位置：

- `src/application/resource_service.py:2069`
- `src/validation/output_guard.py:125`
- `src/validation/pipeline.py:35`

当前落库调用为：

```python
validation_pipeline.validate_resource_card(card)
```

没有传入 `ground_truth_context`。因此现有 Pole-2/NLI 能力在资源生成主链路中被跳过，实际主要检查：

- 内容安全；
- 代码或公式基本语法；
- 正文是否出现规范节点标题；
- 结构化字段是否合法。

“出现了正确标题”不等于“内容事实正确”。这是当前最高优先级的质量缺口。

改造原则：

- 不直接对整张长卡片和整段知识库做一次粗粒度相似度判断；
- 将内容拆成可核验的原子声明；
- 每条声明绑定一至多个 `source_ref_id`；
- 对关键声明执行证据蕴含检查；
- 无法证明的声明进入定向修复或降级，不直接入库。

### P0-2：引用 ID 会被服务端自动补齐，引用存在不代表声明被证据支持

涉及位置：

- `src/resource_generation/generator.py:87`
- `src/resource_generation/generator.py:104`

当模型没有给出有效引用时，`_bind_source_ref_ids()` 会自动附加默认证据 ID。这样能够防止伪造引用，但也会产生“形式上有引用，实质上没有建立声明与证据关系”的问题。

改造原则：

- 保留服务端过滤未知引用的安全能力；
- 取消对模型遗漏引用的静默补齐；
- 引入字段级 `evidence_map`；
- 对缺少证据的关键字段返回 `evidence_missing`，只修复对应字段；
- 非事实性教学内容，例如反思问题、练习提示，可以标记为 `instructional`，不要求事实引用。

### P0-3：默认检索过窄，且 `course_id` 未真正参与查询过滤

涉及位置：

- `src/resource_generation/context.py:151`
- `src/resource_generation/context.py:168`
- `src/resource_generation/context.py:371`
- `src/vector/elasticsearch_knowledge_base.py:625`

当前默认行为：

- 只用节点标题进行一次 BM25 词法查询；
- 最多返回 5 条；
- 每条截断到 1600 字符；
- `course_id` 被写入返回元数据，但没有作为 Elasticsearch filter 传给查询；
- 没有去重、覆盖度控制、重排和总 token 预算；
- 一次远程异常会把进程内 RAG 永久关闭。

这会直接导致证据过窄、重复、缺少例题/误区/边界，甚至存在跨课程召回风险。

### P0-4：提示词没有硬性规定输出语言，少量示例均为英文

涉及位置：

- `src/resource_generation/prompts.py:46`
- `src/resource_generation/prompts.py:89`
- `src/resource_generation/prompts.py:108`

虽然 `locale` 被放进上下文，但系统提示没有要求：

- 标题、正文、选项、解释必须使用目标语言；
- 代码标识符是否允许英文；
- 专业术语第一次出现时如何处理中英文；
- 引用原文与解释语言不一致时如何处理。

当前 few-shot 只有概念图和代码卡，并且都是英文。模型很容易受到英文示例风格牵引。

### P1-1：五张卡没有共享“教学蓝图”

当前概念图先生成，但后续 supporting bundle 只重新接收原始 `ResourceContext`，没有使用已经生成的：

- 核心声明；
- 学习目标；
- 前置知识缺口；
- 误区；
- 例子；
- 术语规范；
- 难度策略。

结果是五张卡可能：

- 重复同一段定义；
- 对复杂度、前置条件或术语给出不同说法；
- 诊断题考查了概念卡没有讲过的内容；
- 练习和代码示例没有覆盖真正的薄弱点。

### P1-2：个性化字段存在，但没有形成明确教学策略

涉及位置：

- `src/resource_generation/context.py:272`
- `src/resource_generation/prompts.py:112`

上下文包含 `mastery_bucket`、`error_signature`、`learning_stage`、`recent_diagnostic` 和 `cognitive_style`，但 prompt 没有定义这些字段应该如何改变内容。

建议：

- `foundational`：减少同时引入的概念数量，补前置知识，使用具体例子和逐步解释；
- `developing`：强调机制、正常案例、边界案例和常见错误；
- `proficient`：增加比较、权衡、变式和迁移；
- `advanced`：增加证明思路、反例、复杂度边界和设计取舍；
- `error_signature`：决定误区解释、干扰项和定向练习；
- `learning_stage`：决定讲解、练习、诊断、复习的比例；
- `cognitive_style` 仅用于呈现偏好，不用于推断学习能力或改变事实内容。

### P1-3：supporting bundle 的统一 token 预算容易造成卡片内容竞争

涉及位置：

- `src/resource_generation/prompts.py:18`
- `src/resource_generation/generator.py:347`
- `src/orchestration_runtime.py:602`

四张支持卡共用 2800 输出 token。模型需要同时满足四套复杂 Schema，容易出现：

- 后面的卡片明显更短；
- 某张卡缺失后直接模板降级；
- 资源间内容机械重复；
- 诊断题干扰项质量不足；
- 代码解释、练习提示被压缩。

建议保留概念图优先，之后按教学功能拆成两个并行子包：

- “示例与解释”：`code_snippet` + `video_summary`
- “练习与诊断”：`interactive_exercise` + `diagnostic_quiz`

每个子包都接收同一教学蓝图，并允许失败卡片单独修复。

### P1-4：代码只检查语法，不检查行为正确性

涉及位置：

- `src/resource_generation/validator.py:46`
- `src/resource_generation/schemas.py:68`

当前 `ast.parse()` 只能证明代码可解析，不能证明：

- 代码解决了当前节点对应的问题；
- 边界测试与代码行为一致；
- 复杂度说明正确；
- 生成示例与实际 `practice_problem_id` 一致；
- 示例没有引入隐藏的无限循环或危险调用。

### P1-5：练习和诊断的“可评分部分”仍偏通用

涉及位置：

- `src/application/resource_service.py:218`
- `src/application/resource_service.py:274`
- `src/application/resource_service.py:2031`

交互练习卡会附加一个服务端生成的通用选择题。该题主要围绕“先说条件、再验证边界”的通用方法，未必与模型生成的具体练习一致。

诊断题虽然新链路会保留模型问题，但只校验：

- 题数；
- 四个选项互异；
- 覆盖 concept/understanding/application 三层。

没有验证唯一正确答案、干扰项合理性、题干歧义、目标覆盖和证据支持。

### P1-6：视频缺失时仍可能产生虚假的时间线表达

`video_url` 可以为空，但 `timeline` 当前要求至少一项。模板会给出 `00:00`，容易让用户误以为存在真实视频时间轴。

应明确区分：

- `trusted_video_available`
- `no_trusted_video`
- `video_metadata_incomplete`

没有可信视频时，不生成时间戳，改为“微课阅读提要”或隐藏视频入口。

### P2-1：缺少内容质量分数、人工反馈和学习效果归因

当前已有 `content_viewed`、`hint_requested`、`answer_submitted`、`code_submitted`、`lesson_completed` 等事件，但没有按资源版本聚合内容质量。

现有数据库模型虽然出现 `quality_score`，但生成作业和资源契约没有形成完整使用闭环。

## 3. 目标生成架构

建议使用以下六阶段流水线：

```text
课程图谱 + 学习者状态
        |
        v
多路检索与证据包 EvidencePack
        |
        v
教学蓝图 LearningBlueprint
        |
        +----------------------+----------------------+
        v                      v                      v
概念卡                 示例与解释子包          练习与诊断子包
        |                      |                      |
        +----------------------+----------------------+
                               |
                               v
结构校验 + 事实校验 + 教学质量校验
                               |
                     失败字段定向修复，最多 1 次
                               |
                               v
版本化缓存、SSE 发布、质量事件与反馈
```

关键设计：

- `EvidencePack` 决定模型“能依据什么写”；
- `LearningBlueprint` 决定五张卡“共同教什么”；
- 每张卡只负责一种教学功能；
- 校验失败优先修复字段，而不是整张重新生成；
- 质量元数据随资源一起持久化和缓存。

## 4. 数据结构改造

### 4.1 EvidencePack

建议在 `src/resource_generation/context.py` 新增：

```python
class EvidenceItem(BaseModel):
    ref_id: str
    title: str
    excerpt: str
    content_kind: Literal[
        "definition", "mechanism", "example", "counterexample",
        "misconception", "complexity", "code", "video"
    ]
    relevance_score: float
    course_id: str
    node_ids: list[str]

class EvidencePack(BaseModel):
    items: list[EvidenceItem]
    query_variants: list[str]
    coverage: dict[str, bool]
    retrieval_mode: str
    total_tokens: int
    degraded_reason: str | None
```

至少覆盖：

- 定义/核心机制；
- 前置条件；
- 一个正常例子；
- 一个边界或反例；
- 常见误区；
- 复杂度或适用限制；
- 代码或视频证据在相应资源需要时按需加入。

### 4.2 LearningBlueprint

建议在 `src/resource_generation/schemas.py` 新增：

```python
class LearningObjective(BaseModel):
    id: str
    action: str
    success_criterion: str
    difficulty: Literal["foundational", "developing", "proficient", "advanced"]
    evidence_ref_ids: list[str]

class AtomicClaim(BaseModel):
    id: str
    text: str
    evidence_ref_ids: list[str]
    importance: Literal["critical", "supporting"]

class LearningBlueprint(BaseModel):
    canonical_title: str
    locale: str
    terminology: dict[str, str]
    objectives: list[LearningObjective]
    claims: list[AtomicClaim]
    prerequisite_refresh: list[str]
    misconceptions: list[dict[str, str]]
    worked_example_plan: dict[str, Any]
    boundary_case_plan: dict[str, Any]
    transfer_target: str
    difficulty_strategy: dict[str, str]
    card_assignments: dict[str, list[str]]
```

`card_assignments` 明确每张卡覆盖哪些 objective/claim，防止五张卡重复。

### 4.3 公共资源字段

所有卡片增加：

```python
objective_ids: list[str]
evidence_map: list[{
    "field_path": str,
    "claim_ids": list[str],
    "source_ref_ids": list[str],
}]
language: str
quality_profile: {
    "schema_score": float,
    "grounding_score": float,
    "pedagogy_score": float,
    "coherence_score": float,
    "overall_score": float,
    "gate_status": str,
}
```

### 4.4 分卡 Schema 强化

`concept_map`：

- 增加 `worked_examples`、`non_examples`、`comparison_points`；
- `learning_objectives` 改为结构化目标；
- Mermaid 节点必须来自蓝图术语，不允许额外发明概念；
- 每个误区包含 `misconception`、`why_wrong`、`correct_rule`。

`code_snippet`：

- 增加 `problem_binding_id`、`input_contract`、`output_contract`；
- 测试用例改为结构化可执行输入；
- 增加 `trace_table` 和 `correctness_invariant`；
- 复杂度说明拆为 `time_complexity`、`space_complexity`、`reason`；
- 代码必须与实际 practice binding 一致。

`interactive_exercise`：

- 增加 `student_artifact`，明确学生最终要提交什么；
- checkpoint 改为 `{criterion, evidence, feedback}`；
- hint 改为 `{level, text, reveals_answer}`；
- 将服务端评分题正式纳入 Schema，由蓝图和错误标签驱动；
- 增加简单 rubric，不再附加与正文脱节的通用题。

`video_summary`：

- 增加 `media_status`；
- `timeline` 在无可信视频时允许为空；
- 每个时间段必须绑定可信 source ID；
- 无视频时输出 `reading_sequence`，而不是伪造时间轴。

`diagnostic_quiz`：

- 每题绑定 `objective_id`、`claim_ids`、`source_ref_ids`；
- 每个干扰项绑定一个具体 misconception/error tag；
- 增加 `answer_rationale` 和 `distractor_rationales`；
- 至少包含一个边界题和一个迁移题；
- 难度根据掌握度分布，不再全部固定为 medium。

## 5. 检索质量改造

### 5.1 多路查询

不要只查询节点标题。为每个节点生成受控查询：

1. `节点标题 + 定义 + 核心机制`
2. `节点标题 + 前置条件 + 适用条件`
3. `节点标题 + 示例 + 边界 + 反例`
4. `节点标题 + 常见错误 + 误区`
5. 代码卡需要时：`节点标题 + Python + 实现 + 复杂度`
6. 视频卡需要时：`节点标题 + video`

查询模板应由服务端确定，不让模型自由生成任意检索词。

### 5.2 强制课程过滤

知识库索引增加稳定的顶层字段：

- `course_id`
- `node_ids`
- `content_kind`
- `locale`
- `content_version`

检索必须传入 filters。没有可验证 `course_id` 的记录不得进入资源证据包。

### 5.3 去重、重排与覆盖度

候选召回 20 条，经过：

1. 相同 `document_id + section` 去重；
2. 内容近似去重；
3. 课程和节点过滤；
4. BM25/向量混合重排；
5. 按 `content_kind` 做覆盖选择；
6. 最终保留 6-10 条。

总输入预算建议控制在 5000-7000 tokens，其中：

- 蓝图证据 3000-4000；
- 学习者状态 500-800；
- Schema 和指令 1500-2200；
- 避免把五条 1600 字符引用无差别全部序列化。

### 5.4 检索降级

将进程永久禁用改为熔断器：

- 连续 3 次失败后 open；
- 30 秒后 half-open；
- 成功一次恢复；
- 记录 `retrieval_mode` 和 `degraded_reason`；
- 课程图谱 fallback 只能支持基本介绍，不得伪装为完整知识证据。

## 6. Prompt 改造

### 6.1 分为四类 Prompt

在 `src/resource_generation/prompts.py` 中拆分：

- `build_blueprint_messages`
- `build_card_messages`
- `build_bundle_messages`
- `build_repair_messages`

### 6.2 硬性语言规则

系统指令必须明确：

- 所有学习者可见文字使用 `context.locale`；
- `zh-CN` 下使用简体中文；
- 代码、API 名称和标准术语可以保留英文；
- 首次出现必要英文术语时使用“中文名（English term）”；
- 禁止因英文 few-shot 改变输出语言。

为 `zh-CN` 提供五类卡片的中文 few-shot，并按 card type 分开维护。

### 6.3 明确个性化决策表

Prompt 中直接提供教学策略，不让模型自行猜测字段含义：

| 学习者状态 | 内容策略 |
| --- | --- |
| foundational | 前置刷新、具体例子、短步骤、低术语密度 |
| developing | 机制解释、正常案例、边界案例、误区修正 |
| proficient | 比较、取舍、变式、复杂度 |
| advanced | 证明、反例、迁移、设计选择 |
| recent error | 进入误区说明、练习题和干扰项 |
| review stage | 减少重复讲解，增加提取练习和间隔复测 |

### 6.4 生成约束

每次生成必须：

- 只使用蓝图中的 claim 和 evidence；
- 明确覆盖的 objective IDs；
- 不知道时省略或标记证据不足；
- 不得把课程图节点名称当作事实证据；
- 不得重复其他卡片已分配的主体内容；
- 练习和诊断不得直接泄露答案；
- 代码和复杂度必须与实际问题 binding 一致。

## 7. 质量校验与定向修复

### 7.1 质量门分层

第一层，确定性校验：

- Pydantic Schema；
- 语言一致性；
- 引用 ID 合法；
- objective/claim ID 合法；
- Mermaid 解析；
- Python AST 和禁用调用；
- 视频 URL/source 匹配；
- 题目选项去重；
- 资源间重复度。

第二层，证据校验：

- 对 `AtomicClaim` 和 `evidence_map` 执行 NLI；
- critical claim 阈值建议 `>= 0.85`；
- supporting claim 阈值建议 `>= 0.75`；
- 不应使用当前字符级/词频近似结果作为唯一生产事实判定；
- NLI 不可用时，critical claim 不得获得“已验证”状态。

第三层，教学质量校验：

- 每个目标是否被至少一张讲解资源和一张练习/诊断资源覆盖；
- 练习是否要求产生可观察结果；
- 提示是否逐级增加信息；
- 诊断题是否具有唯一答案；
- 干扰项是否对应真实误区；
- 难度是否符合当前 mastery bucket；
- 五张卡的关键术语、定义和复杂度是否一致。

### 7.2 定向修复

校验失败后不立即整卡模板降级。生成：

```python
RepairRequest(
    card_type=...,
    invalid_fields=[...],
    issue_codes=[...],
    original_payload=...,
    allowed_claims=...,
    allowed_evidence=...,
)
```

只允许修改失败字段，最多修复 1 次。仍失败时：

- 单卡切换备用 provider；
- 再失败才进入高质量本地模板；
- 其他已经通过的卡不受影响。

### 7.3 代码验证

在隔离执行器中：

- 编译/解析；
- 运行公开测试；
- 运行由服务器维护的隐藏边界测试；
- 验证生成的 `boundary_tests.expected`；
- 设置 CPU、内存、时间、网络和输出限制；
- 静态阻止文件、进程、网络等危险调用。

只有执行通过才能标记 `code_verified=true`。

### 7.4 诊断题验证

至少执行：

- 答案唯一性检查；
- 题干是否包含答案线索；
- 选项长度和语法风格是否过度暴露正确项；
- 题目与证据的一致性；
- objective 覆盖；
- 同一套题的语义重复度；
- 每个错误选项是否能映射到一个 `error_tag`。

对于高风险题目，可用独立模型进行盲答验证：不给 `answer_index`，若独立模型无法稳定选出同一答案，则进入修复。

## 8. 资源丰富度设计

“丰富”应表现为教学功能更完整，而不是字段无上限增长。

### 概念图

- 一句话直觉；
- 严格定义；
- 成立条件；
- 机制；
- 正例；
- 反例；
- 常见误区及纠正；
- 与前置/后继节点的关系；
- 迁移问题；
- 概念关系图。

### 代码示例

- 问题契约；
- 可运行实现；
- 关键不变量；
- 逐步 trace；
- 正常、空输入、单元素、极端输入测试；
- 时间/空间复杂度及来源；
- 常见错误实现；
- 可执行变式实验；
- 与正式练习题的关系。

### 交互练习

- 明确产出物；
- 3-5 个步骤；
- 每步可检查标准；
- 3 层提示；
- 评分 rubric；
- 一个与错误标签对应的评分 checkpoint；
- 完成后的自我解释问题；
- 错误时的针对性反馈。

### 视频/微课提要

- 可信视频存在时：真实链接、真实时段、每段目标、暂停预测点、复习题；
- 无可信视频时：显示“暂无可信视频”，改为 3-5 分钟微课阅读顺序；
- 不允许伪造 URL、时长或时间戳。

### 诊断题

- 5-7 题；
- 概念、理解、应用、边界、迁移至少各有覆盖；
- 每题解释正确答案，也解释主要干扰项为何错误；
- 基于近期错误调整干扰项；
- 难度分布随 mastery 改变；
- 复测题必须保持目标等价但表面形式变化。

## 9. 质量评分体系

建议每张卡计算 0-100 分：

| 维度 | 权重 | 说明 |
| --- | ---: | --- |
| 事实准确性 | 30 | critical claims 是否被证据支持 |
| 证据完整性 | 15 | 字段级引用覆盖率 |
| 教学设计 | 20 | 目标、例子、误区、练习、反馈是否完整 |
| 个性化 | 15 | 是否针对 mastery/error/stage 做实质调整 |
| 可验证性 | 10 | 代码、练习、题目是否可判定 |
| 资源协同性 | 5 | 与其他卡一致且互补 |
| 语言与表达 | 5 | locale、术语、可读性 |

硬门槛：

- 存在 critical factual error：直接失败；
- critical claim evidence coverage < 100%：失败；
- 总分 < 75：修复或降级；
- 75-84：可发布但标记 `quality_warning`；
- >= 85：正常发布；
- 代码未执行通过：不得显示“已验证”；
- 无可信视频：不得显示真实视频时间线样式。

## 10. 离线评测集

建立 `tests/resource_generation/evals/`：

- 选择至少 30 个代表性节点；
- 每个节点设置 4 种 mastery profile；
- 每种 profile 设置 2-3 个 error signature；
- 覆盖有视频、无视频、有代码、纯理论、边界密集等场景；
- 总计至少 120 个资源 bundle 场景。

每个场景保存：

- 输入上下文；
- 允许证据；
- 预期学习目标；
- 必须出现的关键声明；
- 禁止出现的错误声明；
- 期望错误标签；
- 代码隐藏测试；
- 诊断题目标分布。

自动指标：

- Schema pass rate；
- locale pass rate；
- critical evidence coverage；
- unsupported claim rate；
- code execution pass rate；
- quiz answer consistency；
- objective coverage；
- cross-card semantic duplication；
- fallback rate；
- average quality score。

人工抽检 rubric：

- 是否讲对；
- 是否讲清；
- 是否适合当前学生；
- 练习是否真能检验理解；
- 五张卡是否形成完整学习路径。

## 11. 线上效果指标

不要只看生成成功率和停留时长。按 `content_version + model + prompt_version + card_type` 聚合：

正向指标：

- 资源展开率；
- 概念卡后进入练习的比例；
- 首次诊断正确率是否落在合理区间；
- 练习后复测提升；
- 代码首次通过率和重试后通过率；
- 完成节点比例；
- 复习后保持率；
- 收藏、笔记和有效回看。

负向指标：

- 单卡重新生成率；
- 查看资源后立即向 Tutor 询问同一基础概念；
- 题目多次作答仍无提升；
- hint 使用率异常高；
- 诊断题所有用户集中选择同一错误项；
- “不准确/太浅/太难/与当前主题无关”反馈率；
- template fallback 和 partial fallback 比例。

增加显式反馈：

- 有帮助；
- 太浅；
- 太难；
- 不准确；
- 例子不相关；
- 题目有歧义。

反馈必须绑定：

- `resource_id`
- `content_version`
- `prompt_version`
- `model`
- `card_type`
- `node_id`

## 14. 分阶段实施

### 阶段 A：真实性底座，3-5 个工作日

必须完成：

- locale 硬约束和中文 few-shot；
- course filter；
- EvidencePack 与 token budget；
- 落库时启用真实 evidence 校验；
- 引用不再静默伪装为已 grounding；
- RAG 熔断恢复；
- 无视频状态修复。

验收：

- 中文合规率 >= 99%；
- 跨课程召回为 0；
- critical claim evidence coverage = 100%；
- 无可信视频时伪时间线为 0。

### 阶段 B：教学蓝图与资源协同，5-8 个工作日

必须完成：

- LearningBlueprint；
- objective/claim/card assignment；
- supporting 子包拆分；
- 五类中文 few-shot；
- mastery/error/stage 决策表；
- 跨卡一致性和重复度检查。

验收：

- objective coverage = 100%；
- 五卡关键定义冲突率 = 0；
- 支持卡语义重复率明显低于 v3；
- 人工教学设计评分平均 >= 4/5。

### 阶段 C：可验证练习与诊断，5-7 个工作日

必须完成：

- 代码执行验证；
- 练习 rubric 和分层提示；
- 蓝图驱动评分 checkpoint；
- quiz 唯一答案、干扰项和证据检查；
- 定向字段修复。

验收：

- 代码执行验证通过率 = 100% 后才发布；
- 诊断题答案一致率 >= 98%；
- 通用练习题与正文脱节率 = 0；
- 单字段修复成功率 >= 70%。

### 阶段 D：质量闭环与发布，4-6 个工作日

必须完成：

- 离线 eval；
- quality score；
- 显式反馈；
- 线上指标；
- shadow/canary；
- resource-v4 缓存隔离。

发布顺序：

1. 离线评测通过；
2. shadow 生成，不向用户展示；
3. 5% canary；
4. 20%；
5. 50%；
6. 100%。

任一阶段出现事实错误率、歧义题率或 fallback 率显著恶化，应停止放量。

## 15. 建议的最终验收标准

内容质量：

- 严重事实错误：0；
- unsupported critical claims：0；
- 中文语言合规率：>= 99%；
- objective coverage：100%；
- 关键定义跨卡冲突：0；
- 代码验证通过率：100%；
- 诊断题答案一致率：>= 98%；
- 视频来源可信率：100%；
- 人工总评分：>= 4.2/5。

系统质量：

- 模板降级率：< 5%；
- 单卡修复后成功率：>= 70%；
- 质量校验增加的 P95 后台生成时间可控；
- 概念卡首屏仍保持优先发布；
- v3/v4 缓存、指标和回滚相互隔离。

学习效果：

- 相比 v3，练习后复测正确率有统计显著提升；
- 相比 v3，单卡重新生成率下降；
- 相比 v3，“不准确/不相关/有歧义”反馈下降；
- 提升不能依赖把题目变简单，应同时监控题目难度与首次正确率分布。

## 16. 实施优先级

建议严格按以下顺序推进：

1. 真实证据校验、课程过滤、语言规则；
2. EvidencePack 和教学蓝图；
3. 五类 Schema 与中文 few-shot；
4. 代码、练习、诊断的可验证性；
5. 单卡定向修复和备用 provider；
6. 质量评分、离线 eval、线上反馈；
7. 前端来源、降级和反馈展示；
8. 分阶段 rollout。

其中前四项决定内容是否真正可靠、有效；后四项决定质量能否稳定运营和持续提高。
